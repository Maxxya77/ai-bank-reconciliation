# AI Bank & Corporate Card Reconciliation V3

은행 거래내역, 법인카드 이용내역, 전체 총계정원장(GL)을 입력하면 **은행 ↔ 보통예금 GL**과 **법인카드 ↔ 카드 미지급금 GL**을 한 화면에서 각각 대사하는 포트폴리오용 프로토타입입니다. 정상 거래를 구분해 담당자가 예외에 집중하도록 돕습니다. ERP를 대체하거나 회계·세무 판단을 자동화하지 않습니다.

Local AI(Ollama)는 업로드 파일의 **컬럼 의미 추론·매핑**과 규칙으로 좁힌 **거래처명 후보 설명**에 사용합니다. 계정 추출, 전표번호 연결, 금액·방향·날짜 계산, 상태·예외 분류는 검증 가능한 Python/JavaScript 규칙으로 처리합니다. AI가 거래를 최종 확정하지 않습니다. 브라우저 데모는 Ollama 없이 규칙·수동 컬럼 매핑과 거래처 정규화·별칭을 제공합니다.

## 실행

Python 3.11 이상, Node.js는 테스트용입니다. `app.py`가 있는 폴더에서:

```powershell
python -m venv .venv
.\.venv\Scripts\python -m pip install -r requirements.txt
ollama pull qwen2.5:7b
python -m streamlit run app.py
```

Ollama 서버가 연결되지 않으면 규칙 매핑으로 전환합니다. 기본 주소는 `http://localhost:11434`입니다. 브라우저 데모는 `python -m http.server 8765 --bind 127.0.0.1` 후 `http://127.0.0.1:8765`에서 열 수 있습니다. GitHub Pages에는 `index.html`과 `gl.js`를 함께 배포합니다. XLSX 읽기에는 SheetJS CDN이 필요하므로 최초 로딩에 인터넷 연결이 필요합니다.

## 입력과 업무 흐름

| 파일 | 역할 |
| --- | --- |
| `bank_shinhan_checking.xlsx` | 신한은행 주거래계좌 거래내역 |
| `card_shinhan_corporate.xlsx` | 신한 법인카드 이용내역 및 거래 상태 |
| `ledger_full_gl.xlsx` | 복식부기 전체 GL |
| `sample_bank.xlsx`, `sample_ledger.xlsx` | 같은 은행·전체 GL 샘플의 호환용 사본 |

화면에서 은행·카드·GL 파일을 업로드하고 컬럼 매핑을 확인한 뒤 대사를 실행합니다. 샘플 GL에서는 `111001 보통예금-신한`과 `2160 미지급금-신한카드`를 각각 발견합니다. 이 데모는 해당 유형 계정이 각각 하나인 경우 자동 선택합니다. 계정코드 자체는 추출 함수의 고정 상수가 아니므로 다른 회사의 코드도 사용할 수 있습니다.

```text
법인카드 사용 → 비용 / 필요 시 부가세대급금 → 미지급금-신한카드
               카드 이용내역 ↔ 카드 미지급금 대변 대사

월 카드대금 지급 → 미지급금-신한카드 차변 / 보통예금-신한 대변
                  은행 출금 ↔ 보통예금 대변 대사
```

개별 카드 사용 전표에는 보통예금이 없습니다. 카드 대사에서는 **카드 총액과 카드 미지급금 대변**을 비교하며, 부가세를 제외한 비용금액과 직접 비교하지 않습니다. 월 결제 전표의 카드 미지급금 차변은 카드 사용 대사에서 제외하고 은행 대사에만 나타납니다.

전체 GL 컬럼은 `전표번호 / 전기일 / 계정코드 / 계정과목 / 차변 / 대변 / 거래처 / 적요`입니다. GL 거래처는 실제 상대방, 적요는 비용·거래 내용을 설명합니다. 은행 파일에는 거래일자·은행 표시 상대방명·출금·입금·잔액을, 카드 파일에는 `이용일자 / 가맹점명 / 이용금액 / 거래상태 / 승인번호 / 카드번호`의 여섯 컬럼만 담았습니다. 은행 적요를 GL의 내부 비용명처럼 가공하지 않았습니다. 카드 승인번호·마스킹 카드번호는 매핑상 선택 항목입니다. 업로드 파일의 실제 헤더가 달라도 매핑을 확인·수정할 수 있습니다.

## 카드 상태와 데모 가정

| 표준 상태 | 화면 표시 | 원본 값 예시 | 처리 |
| --- | --- | --- | --- |
| `PENDING` | 매입대기 | 매입대기 | GL 매칭·예외 건수에서 제외 |
| `CONFIRMED` | 매입완료 | 매입완료 | GL 사용 전표와 대사 |
| `CANCELLED` | 승인취소 | 승인취소 | GL 매칭·예외 건수에서 제외 |

**카드사마다 거래 상태 명칭과 확정 시점은 다를 수 있으며, 본 프로토타입에서는 미확정/매입대기 상태는 GL 전표 매칭 대상에서 제외하는 것으로 가정했습니다.** 샘플과 화면에는 세 가지 한글 상태만 표시합니다. 다른 카드사의 영문·대체 상태명은 업로드 정규화 단계에서 내부 enum으로 해석할 수 있습니다. 이는 모든 회사의 회계정책을 뜻하지 않습니다. 매입대기 거래에 GL 전표가 없어도 `CARD ONLY`가 아닌 전표처리 대기로 표시합니다. 취소 거래도 별도 표시합니다. 확정 거래에서만 정상 매칭, `CARD ONLY`, `LEDGER ONLY`, `AMOUNT MISMATCH`를 확인합니다. 알 수 없는 상태는 임의로 확정 취급하지 않고 입력 오류로 알립니다.

## 샘플 시나리오와 검증 결과

8월 카드 이용내역 **15건**은 사무용품·문구·회의 음료·식대·택시·주차·통행료·편의점·다이소·배달·숙박·KTX·유류비·카페·인쇄비로 구성됩니다. 클라우드 계약 비용은 카드 샘플에서 제외했습니다. 확정 12건, 미확정 2건, 취소 1건입니다. GL 사용 전표에는 부가세대급금이 있는 3라인 사례 6건과 별도 부가세가 없는 2라인 사례가 함께 있습니다. 이 분류는 샘플 작성 가정이며 세무 적격성을 프로그램이 판단하지 않습니다.

카드 결과는 규칙 기준 정상 매칭 **9건**, 미확정 **2건**, 취소 **1건**, 확인 필요 **4건**입니다. 확인 필요는 `DAON FNB` ↔ `한식당 다온`의 거래처 확인 1건, 확정 카드만 있는 거래 1건, GL만 있는 전표 1건, 금액 차이 1건입니다. Ollama가 연결되어 이름 관계를 제안하더라도 이 건은 **AI 후보 매칭**으로만 표시되어 확인 필요 건수에 남습니다. 카드 확정 총액과 GL 카드 미지급금 발생액은 각각 **847,300원**이고, 9월 8일 `JV-CARD-SETTLE-202608`에서 동일 금액을 신한 보통예금으로 한 번에 지급합니다. 은행 파일의 `SHINHAN CARD` 출금 847,300원은 별칭을 통해 정상 매칭됩니다.

샘플의 카드만 있는 77,000원, GL만 있는 76,000원, 금액 차이 1,000원은 **전체 합계에서는 우연히 상쇄**됩니다. 따라서 합계 일치만으로 개별 거래가 모두 대사됐다고 해석해서는 안 됩니다. 예외 3건은 결과에서 그대로 드러납니다.

은행 대사는 기존 1:1, 날짜 차이, 1:N, N:1, 금액 불일치, 입출금 방향 오류, `BANK ONLY`, `LEDGER ONLY`, 자리바꿈·자릿수 오류 힌트를 유지합니다. 날짜 창은 ±7일, 그룹 후보는 최대 10건·그룹 크기는 최대 4건입니다. 샘플 은행 결과는 **57건 = 규칙상 정상 51건 + 확인 필요 6건**이며, 확인 필요 중 1건은 `KEPCO SEOUL` ↔ `한국전력공사` 이름 차이입니다. 9월 전기요금 76,543원은 은행일과 전표일을 2일 차이로 두어 `MATCHED (날짜 차이)`를, 전기요금 추가 납부 80,000원은 보통예금 차변 기입으로 방향 오류 의심을 보여줍니다. 결과 표의 핵심 7개 열은 데스크톱 너비에 맞추고 헤더를 세로 스크롤 중에도 고정했습니다. 행을 선택하면 날짜·원장금액 등 상세값을 볼 수 있습니다. `JV-VAT`는 광고선전비 1,000,000 + 부가세대급금 100,000을 보통예금 출금 1,100,000과 연결해 상대계정·Google 거래처를 보여줍니다. `JV-NONBANK`는 은행 대사에 포함되지 않습니다.

## 거래처명 비교와 AI 보조

은행은 **방향 → 금액 → ±7일 날짜 → 은행 상대방명과 GL 거래처**, 카드는 **매입상태 → 이용금액과 카드 미지급금 대변 → ±7일 날짜 → 가맹점과 GL 거래처** 순서로 확인합니다. GL 적요는 결과 설명에 사용하며, 이름만 비슷한 적요로 자동 매칭하지 않습니다. 거래처는 정확 일치, `(주)`·`㈜`·`주식회사`·공백·기호·영문 대소문자 제거 후 일치, 명시적 별칭 순서로 비교합니다. `한전`·`KEPCO` ↔ `한국전력공사`, `SHINHAN CARD` ↔ `신한카드` 등이 별칭입니다. 별칭은 [party.py](party.py)와 [gl.js](gl.js)의 작은 사전으로 시작했습니다.

방향·금액·날짜가 맞지만 이름이 해결되지 않으면 **거래처 확인 필요**로 남깁니다. 후보가 여러 개면 후보명을 보여주고 어느 것도 자동 확정하지 않습니다. Streamlit 앱은 Ollama가 연결된 경우 이처럼 좁혀진 단일 후보의 이름만 JSON으로 질문해 이유를 표시할 수 있습니다. 긍정 응답도 **AI 후보 매칭**일 뿐 정상 `MATCHED`로 승격하지 않습니다. Ollama가 없거나 응답이 불명확하면 규칙 대사와 예외 분류는 그대로 작동합니다. 브라우저는 Ollama를 호출하지 않아 미해결 이름을 **거래처 확인 필요**로 표시합니다. AI의 confidence는 회계상 확정 근거로 사용하지 않습니다.

모든 샘플 GL 전표는 차변합계와 대변합계가 같습니다. 전체 GL의 거래처는 실제 상대방, 적요는 거래 내용으로 구분했습니다.

## 보고·검토 및 제한

화면은 은행 대사와 법인카드 대사 두 탭으로 구성됩니다. 두 결과 표는 세로 스크롤 중 헤더를 고정하고, 핵심 금액과 전표 정보를 우선 보여줍니다. 카드 대사는 카드 이용금액과 GL 카드 미지급금 대변을 비교하며, 부가세대급금은 전표 상세 정보에서 확인합니다. 기존 은행 예외 확인 상태는 Streamlit의 `reviewed.db`에 저장됩니다. 브라우저는 확인완료 영구 저장 기능이 없습니다.

- 여러 은행 보통예금 또는 여러 카드 미지급금 계정이 동시에 발견되면 데모가 임의 선택하지 않고 안내합니다. 다중 계정별 선택은 향후 확장 대상입니다.
- 전표번호는 업로드 범위에서 유일해야 하며, 한 전표에 여러 카드 사용이 섞이면 전표 전체 상대 정보를 보여줍니다. 카드 승인번호의 GL 측 직접 연결은 아직 구현하지 않았습니다.
- 확정 후 취소와 역분개, 부분취소·할부·해외통화·카드 청구 주기 차이 등은 구현 범위 밖입니다.
- 1:1 카드 매칭은 금액·±7일·가맹점/GL 거래처 정보를 사용합니다. 이름이 다르면 수동 확인이 필요하며, 우연한 동액 또는 그룹 합계는 담당자가 검토해야 합니다.
- 첫 시트·첫 행 헤더를 사용합니다. Python CSV는 UTF-8/CP949/EUC-KR, 브라우저 CSV는 UTF-8입니다. 계정코드는 회사별 차트를 추측하지 않고 계정명에서 후보를 찾습니다.

검증: `python -m unittest discover -s tests -v`. Python과 JavaScript의 은행·카드 정규화, 계정 추출, 상태·매칭 행 및 샘플 데이터 동일성을 검사합니다. 상세 기록은 `TEST_RESULTS.md`에 있습니다.
